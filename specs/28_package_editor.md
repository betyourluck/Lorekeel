## 動機

パッケージの改変・自作の導線は今、**アプリの外**にある。「フォルダを開く」（2026-07-28）で
エクスプローラへ出て、汎用エディタで YAML を書き、アプリに戻って新しいゲームを始めて
開幕の ⚠ を読む — もしくは `play lint` を叩く。この往復には二つの摩擦がある。

1. **書く場所と検める場所が別。** `play lint` は「作らせる → 検める」のループを軽くしたが、
   検査結果は端末に出て、直す場所はエディタで、名指しされたキーを目で探すことになる。
2. **汎用エディタは Kataribe の語彙を知らない。** `entiity` の typo も、`locations` に無い
   行き先も、宣言していないフラグも、書いている瞬間には何も言われない。死んだ参照 lint
   （spec 21/25 同梱）が捕まえる誤りの大半は、**書いた瞬間に補完と赤線があれば起きない**。

編集モードはこの二つを畳む: アプリの中で YAML を開き、書いている手元に診断を出し、
Kataribe の語彙（キー名・宣言済み id）を補完する。**パッケージの形式は 1 バイトも変えない**
（エディタは書き方を助ける道具であって、仕様の変更ではない — outcast `package_spec.md` への
波及なし）。正本・prompt・キャッシュも無風（提示層どころか、プレイの外の道具）。

## 前提の訂正 — 「LSP 準拠」ではない

導入済みの CodeMirror 6 は **LSP クライアントを内蔵しない**。持っているのは
診断（`@codemirror/lint` — `linter(source)` に Diagnostic 列を返させる拡張点）と
補完（`@codemirror/autocomplete` — completion source）で、これは LSP が提供するのと
**同種の機能をプロトコル無しで挿せる口**である。

Kataribe にとってはこちらの方が正しい形になる — 検査規則は全部 Rust 側に既にあり
（`unknown_key_lints` / `Scenario::validate` / `Scenario::lints` / `manifest_lints` /
`character_lints` = `harness::inspect` が束ねる 5 系統）、**LSP サーバという別プロセスと
プロトコル実装を挟む理由が無い**。Tauri command で直接呼び、返りを CodeMirror の
拡張点へ流す。新しい検査規則は作らない（`play lint` と同じ収縮の判断 — 入口を増やすだけ）。

## 何を作るか

### A. 編集モードの骨格

1. **トグル**: ヘッダ帯のタイトル横に鉛筆アイコンのトグルボタン。ON で編集モード。
   対象パッケージは**選択中のパッケージ**（`store.packagePath`。プレイ中ならそのパッケージ）。
   未選択なら押せない（disable + title で理由）。**卓（multiplayer）がアクティブな間も
   押せない**（→「卓との排他」節）。
2. **編集セッションの登録（TOCTOU 封じ）**: ON 時に新 command `open_editor(package)` が
   backend に**編集ルートを登録**する。以後の読み書き command は相対パスだけを受け取り、
   登録済みルートから解決する — frontend がフルパスを毎回渡す形にしない
   （保存の瞬間に選択パッケージが切り替わっていた、という TOCTOU を構造的に消す）。
   OFF で `close_editor`（登録解除）。
3. **画面**: ヘッダと右ペインは変わらない。**会話ペインと入力欄が丸ごとエディタ領域に
   差し替わる**（表示の差し替えのみ — プレイ状態・会話ログは破棄せず、OFF で元に戻る。
   タブ切替と同じ揮発性）。
4. **ファイル一覧**: 右ペインの縦タブに「ファイル」タブが増える（編集モード中のみ表示 —
   `facts` タブの `v-if` と同じ機構。OFF で消え、選択中なら**編集モードに入る直前にいた
   タブへ戻す**）。フォルダでカテゴライズして列挙:
   - パッケージ直下: `package.yaml`（campaign entry なら `campaign.yaml` も）
   - `scenarios/*.yaml`
   - `characters/*.yaml`
   - `memoria/*.yaml`
   **各フォルダ直下のみ**（サブディレクトリは列挙しない — パッケージ形式自体が
   直下参照なので再帰の需要が無い。将来形式が変わればその spec が広げる）。
   **YAML だけ**（画像・音声はテキストエディタの対象外 — 一覧にも出さない。
   眺めたければ既存の「フォルダを開く」）。クリックでエディタに開く。
   書庫由来（`.kataribe_source.json` あり）ならタブ上部に薄いバッジ
   「書庫版 — 保存するとフォーク」（初回保存の確認が唐突にならない事前認知）。
5. **エディタ**: `CodeEditor.vue`（spec 27 Phase C の器）に `yaml` 言語を追加
   （`@codemirror/lang-yaml` — spec 27 が「着手する時に足す」と予告した依存）。
   Ctrl+S で保存。既存の history（undo/redo）・検索・テーマ追従はそのまま効く。
6. **保存**: 新 command `save_package_file(rel_path, text, fork: bool)`。backend の判定順は
   **①卓ガード → ②パス検証 → ③原子書き込み → ④（fork 時のみ）出所メタ削除**。
   - **パス検証**: 登録済み編集ルート内、上記カテゴリ直下の `.yaml` のみ。
     パス要素検証（`..`/絶対パス拒否）+ **シンボリックリンク解決後の containment**
     （canonicalize してルート配下を確認 — `resolve_asset` と同じ規律）。
   - **原子書き込み**: tmp→rename（`save_session` と同じ流儀 — 書きかけで配布物を壊さない）。
   - **メタ削除は書き込み成功の後**（同一 command 内）: 逆順だと保存失敗時に
     「フォーク済みなのに中身は書庫版のまま」という半端が残る。削除自体の失敗は
     警告として返すだけ（次の保存で再試行される。保存本体は成功している）。
   - **v1 base は編集のみ**。新規作成は Phase D（characters/ のみ）が乗って v1 完成形、
     削除・リネームは v2（消す操作は誤爆の重みが違う）。
7. **未保存の守り（● マーカー）**: 未保存の変更があるファイルには ●。確認（破棄 or 保存）を
   挟む契機は **(a) ファイル切替 (b) 編集モード OFF (c) パッケージ切替**（編集モード中の
   切替は強制 OFF と同じ経路）**(d) アプリ終了**（`onCloseRequested` で未保存があれば確認）。

### B. フォーク — spec 17 との衝突の解消（方針は決定済み）

書庫由来のパッケージ（`.kataribe_source.json` あり）を編集して保存すると、`tree_hash` が
変わり更新機構が「編集されています」警告を出す。方針は spec 27 波及節で決定済み —
**編集したらフォーク＝別パッケージ扱い**（出所メタを外せば手動配置扱いになる既存経路）。

具体化: 書庫由来パッケージで**初回の保存時**に確認ダイアログ
「このパッケージは書庫から取得したものです。編集して保存すると、以後は書庫の更新の
対象外になります（あなたの改変版として扱われます）」→ OK で `fork: true` の保存
（書き込み成功 → メタ削除、A.6 の順序）。キャンセルなら何もしない。**黙って外さない** —
更新が来なくなるのは不可視で不可逆な変化なので確認を挟む（シードリセット・「入れ直す」と
同じ線）。事前認知は A.4 のバッジが担う。手動配置（メタ無し）のパッケージは確認なしで
普通に保存（`fork: false`）。

### C. 診断 — 二層

既存 lint の正直な制約: **メッセージは文字列で、行番号を持たない**（YAML パス
`locations.cell.gate: ...` は持つ）。エディタの赤線には位置が要るので、確実に取れるものと
近似で当てるものを分けて二層にする。

1. **層 1 — エディタ内（打鍵デバウンス 300〜500ms、単一ファイルで完結する検査だけ）**:
   新 command `lint_editor_text(kind, text) -> Vec<EditorDiagnostic>`。
   `kind` はファイル一覧のカテゴリから決まる。kind ごとの検査内容:
   - `manifest`（package.yaml）: parse + `manifest_lints`
   - `scenario`: parse + `unknown_key_lints`
   - `character`: parse + `character_lints`
   - `campaign` / `memoria`: **parse のみ**（専用の未知キー lint は現存しない。
     `character_lints` と同型（`struct_keys` から導出）で組めるが、v1 は見送り —
     どちらも欄数が少なく、欄名 typo の実害も未観測。観測されたら同型で足す）
   - **parse エラー**（serde_yaml）: `Location`（行・列）を持つので**正確な位置**に赤線。
   - **未知キー lint**: 位置は**パスの親キー列を順に前方検索して範囲を絞る**近似
     （`locations.cell.gate` なら `locations` の行 → その先で `cell` → その先で `gate`）。
     終端キーだけの単純検索は `id`/`name` 級の頻出キーで別の行に赤線を引く誤爆になるので
     採らない。それでも一意に絞れなければ**位置なし**（行を偽らずパネル表示のみ、
     文面に「位置未確定」を添える）。
   - `EditorDiagnostic { line: Option<u32>, severity, message }`。
   - CodeMirror 側は `linter()` の source としてこの command を await するだけ
     （デバウンスは linter 拡張の既定機構。応答前に次の打鍵が来たら古い結果は捨てる）。
2. **層 2 — 保存時（パッケージ全体）**: 保存成功後に `inspect_package`（既存）を走らせ、
   結果（errors / warnings）を「ファイル」タブの下部に一覧表示。**ファイル横断の破れ
   （幻フラグ・幻 goal・死んだ参照・cast 不整合）はここでしか出ない** — validate は
   注入（cast / package）後の Scenario に掛かるので、単一ファイルの層 1 では原理的に
   検査できない。
   - **帰属の整形を足す**（波及に計上）: 現在の `InspectReport` のメッセージは接頭辞の
     形式が系統ごとに揺れる（`characters/{name}:` / `{id}: {path}` / 接頭なし）。
     app 側で `EditorIssue { file: Option<RelPath>, message }` へ写す整形層を足し、
     一覧の各行に**該当ファイル名を明示**する（保存したファイル以外が壊れたとき —
     package.yaml のフラグ改名で scenarios/ 側の参照が死ぬ等 — 「どのファイルの話か」が
     直感的に伝わる）。file が引けた行はクリックでそのファイルを開く。整形は表示の話で
     検査規則ではない。
3. **境界の明示**（`inspect` の doc から継承）: 緑は「読める」であって「遊べる」ではない。
   独立に正しい機構どうしの相互作用（`flag_hints` × `hidden_flags` の実例）は原理的に
   捕まらない。ファイルタブの一覧が空のときも「全ゴールへの到達経路は手でたどってください」
   を薄字で常設する。

### D. 補完 — Kataribe の語彙

新 command `editor_vocabulary() -> EditorVocabulary`（登録済み編集ルートを読む）。
二種の語彙を返す:

1. **キー名**: `gm_core::struct_keys`（既に pub、型から導出）+ enum バリアント表
   （`lint.rs` の `variant_keys` — pub 化が要る）。**手書きの語彙表は作らない**
   （未知キー lint と同じ規律 — フィールド追加に自動追従、lint と補完が同じ表を見るので
   「補完に出るのに lint に叱られる」乖離が構造的に起きない）。
2. **宣言済み id**: 編集ルートのパッケージを読んで集める — locations / `allowed_flags` /
   items（場所アイテム + 初期所持）/ entities（characters + cast）/ challenges / contests /
   skills / goals。**値の補完はキー補完より効く** — 死んだ参照 lint が捕まえる誤り
   （`to: piit` / 幻 entity / 幻 challenge）は全部 id の typo で、補完は同じ誤りの
   **上流での予防**になる。

**語彙のソースはディスク**（保存済みの状態）。ゆえに未保存バッファ内の id 変更・新設は
補完に反映されない — **保存成功時に語彙を再取得**する（Phase D の新規作成後も同様）。
編集中バッファから同一ファイル内の宣言 id を拾う形が理想だが v2（構文木からの抽出が要る）。

補完の文脈判定（「いまカーソルは gate の中か op の中か」）は v1 では簡易に留める:
直近の親キー（インデントを遡って最初に浅くなる行のキー）で候補集合を絞り、
判別できなければ全キーを出す。Lezer 構文木での厳密な文脈解決は v2（診断の位置精密化と
同じ技術なので、やるなら一緒に）。

## 反映のタイミングと、プレイ・卓との整合

- **保存はファイルに書くだけ**で、メモリ上の `GameSession` には触れない。反映は
  **次の「新しいゲーム」またはロードから**。プレイ中に保存したらトーストで
  「次の『新しいゲーム』またはロードから反映されます。現在のセッションには影響しません」
  と明示（`SessionSave` は骨格を保存せず content パスを参照する既存仕様が、そのまま
  「編集がロードで生きる」を保証する。黙って効かないのは不信の元）。
- **卓との排他（入口で塞ぐ）**: パッケージの content hash は `package_match` / relay
  キャッシュの鍵で、卓の最中に変わると「ホストのロード/新規が卓を黙って壊す」既知の穴と
  同型の壊れ方をする。**保存時に拒否する形は採らない** — 編集させておいて Ctrl+S で
  初めて弾くのは、書いた変更の退避を強いる UX 破綻（査読指摘）。ゆえに:
  - **卓がアクティブな間は鉛筆トグル自体を disable**（tooltip に理由）。
  - **編集モード中は卓を開始できない**（TableDialog 側を disable + 理由。逆向きの穴も塞ぐ）。
  - backend の `save_package_file` にも卓中ガードを残す（**二層** — frontend の disable +
    backend の拒否。`update_site_package` のプレイ中ガードと同型の安全網で、判定順は
    A.6 のとおり最優先）。
- 編集モードの ON/OFF 自体はプレイ状態に触れない（表示の差し替えのみ）。

## 確定済み（旧・未決 4 点 — 査読 2 本とも提案に賛成で確定）

1. **フォーク確認は初回保存時**（開くだけ・読むだけは無害。確認は副作用が発生する瞬間に）。
   事前認知は A.4 のバッジ。
2. **プレイ中の保存は許可 + トースト**（作者のテストプレイ = 動かしながら直すが主用途）。
   **卓中は入口で排他**（上節 — 保存時拒否から入口 disable へ査読反映で強化）。
3. **新規作成は Phase D で characters/ のみ**。作成時はファイル名検証
   （ファイル名 = EntityId になるので `resolve_asset` と同系の保守的な文字集合）+
   最小雛形（`name` / `profile` の空欄）を挿入。作成後は語彙を再取得。削除・リネームは v2。
4. **開幕 ⚠ とエディタ診断は両方残す**（受領者と作者で受け手が違う。文面の正本は
   `inspect_msg` 一つなので二重管理の不整合は起きない）。

## スコープ外（v1）

- LSP サーバ / 外部エディタ連携（上記「前提の訂正」— 立てる理由が無い）
- ファイルのリネーム（削除は 2026-08-27 ユーザーFB で v1 へ昇格 — Status 参照）/
  画像・音声アセットの管理（既存「フォルダを開く」の領分）
- YAML 以外の編集（`README` 等）/ サブディレクトリの列挙
- 診断の行位置の厳密解決・バッファ内 id の補完反映（Lezer 木 — 近似で足りなければ v2 で一緒に）
- `campaign` / `memoria` の未知キー lint（parse のみ。実害が観測されたら
  `character_lints` と同型で足す）
- パッケージの新規作成ウィザード（テンプレートからの雛形生成 — 別の話。ジオラマ
  template の配布で足りるかを先に見る）
- 編集履歴・バックアップ（undo はエディタ内で足りる。ファイル履歴は git の領分）

## Phase 分割

- **Phase A（骨格）**: 鉛筆トグル + 卓排他（両向き）/ `open_editor`・`close_editor`
  （編集ルート登録）/ ファイル一覧タブ + 書庫バッジ / `@codemirror/lang-yaml` 追加 /
  読み込み・保存 command（判定順・パス検証・原子書き込み・fork）/ フォーク確認 /
  未保存確認 4 契機。この時点で「アプリ内で編集して保存できる」が成立
  （診断は開幕 ⚠ と `play lint` が従来どおり受け持つ）。
- **Phase B（診断）**: `lint_editor_text`（kind 別・parse 正確位置 + 未知キー親キー列近似）
  をデバウンス linter へ / 保存時 `inspect_package` + `EditorIssue` 整形（ファイル帰属明示 +
  クリックで開く）/ 境界の薄字常設。
- **Phase C（補完）**: `editor_vocabulary`（`variant_keys` pub 化）/ id 補完 / キー補完 /
  保存時の語彙再取得。
- **Phase D（新規作成）**: characters/ への新規ファイル（名前検証 + 最小雛形 + 語彙再取得）。

## PoC 方針

- backend: パス検証（トラバーサル・カテゴリ外・symlink 脱出の拒否）/ 原子書き込み /
  **fork の順序**（書き込み失敗時にメタが残ること・成功時に消えること・メタ削除失敗が
  警告で返ること）/ `lint_editor_text` の kind 別（parse エラーの行位置が載る・未知キーの
  近似行が親キー列で絞られる・頻出キー名の誤爆をしない・一意に絞れない時は位置なし・
  clean で空）/ vocabulary の型導出（手書き表が無いことの表明 = フィールド追加への
  自動追従を既存 lint テストと同型で）/ 卓中ガード。
- frontend: vue-tsc + vite build + 目視（トグル・卓排他・ファイル切替・●・4 契機の確認・
  赤線・補完・フォーク確認とバッジ）。
- 検査規則そのものは既存テストが持つ（新規則ゼロ）。

## 査読の反映（2026-08-27、2 本）

- **卓中ガードを保存時拒否 → 入口 disable（両向き）へ強化**（査読 2 の UX 破綻指摘。
  backend 拒否は二層目の安全網として残し、判定順を A.6 に凍結 — 査読 1 の順序指摘も
  これで解消）
- **TOCTOU 封じ**: 保存のたびに frontend がパスを渡す形をやめ、`open_editor` の
  編集ルート登録制に（査読 1）
- **フォークのトランザクション**: `fork: bool` を保存 command に載せ、
  書き込み成功 → メタ削除の順を backend 内で閉じる。削除失敗は警告（査読 1・2 が同指摘）
- **未知キーの行近似を終端キー単純検索 → 親キー列の範囲絞り込みへ**。絞れなければ
  位置を偽らず「位置なし」（査読 2 の誤爆指摘）
- **`kind` の定義を明記**: campaign / memoria は parse のみ（専用 lint は現存しない —
  「5 系統を束ねるだけ」の原則を保ち、v1 では新設しない）（査読 1）
- **v1 の書き分け**: base は編集のみ、Phase D（characters/ 新規作成）が乗って v1 完成形（査読 1）
- **タブ復帰先を `progress` 固定 → 直前のタブへ**（査読 1）
- **層 2 の帰属整形（`EditorIssue`）を波及に計上** — 接頭辞形式の揺れは現状保証されて
  いない（査読 1・2 が同指摘）
- **未保存確認の契機を 4 つに明記**（ファイル切替 / OFF / パッケージ切替 / アプリ終了）（査読 1）
- **語彙ソースはディスク + 保存時再取得、バッファ反映は v2 と明記**（査読 1）
- **書庫バッジ**（査読 1・2 が同提案）/ **一覧は直下のみ**（同）/ **デバウンス 300〜500ms**・
  **symlink containment**（査読 1）/ **Phase D の名前検証 + 雛形**（査読 2）
