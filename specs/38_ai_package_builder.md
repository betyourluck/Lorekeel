## 動機（ユーザーの言葉から）

> シナリオ編集モードで現在は 1 ファイルずつ作っていくが、できればまとめて複数ファイルを
> AI 生成で編集し、パッケージを作れるようにしたい。

spec 29（AI 編集）は**対象 1 つ・編集のみ**で作った。どちらもユーザー決定だった
（「一気に作らせようとしないで 1 ファイルずつ」「新規ファイルは作らせなくていい」）。
本 spec はその 2 つを広げる。広げても、spec 29 が退けた誤差の源は今も真である:

1. **仕様の量** — 全部の仕様を渡すと、無関係な節の語彙から幻のキー・幻の参照を書く。
2. **一発生成** — 複数ファイルを 1 応答で書かせると、出力上限で途中が切れ、ファイルをまたぐ
   参照（cast ↔ characters、globals.flags ↔ flag_rules）が片側だけ書かれる。

だから**作者が 1 回頼めば複数ファイルが揃う**ようにするが、**モデルが 1 回で書く量は増やさない**。
複数ファイルの扱いは機械（オーケストレーション）が持ち、モデルには今と同じ「1 ファイル・種別ごとの
仕様・`sd` で少しずつ」の仕事を順に渡す。

## 決定（rev1 の推奨。未決は末尾）

1. **4 段で回す — 計画 → 1 ファイルずつ書く → まとめて検める → 作者が適用**。
   どの段でもモデルが 1 回に書くのは 1 ファイルの一部だけ。
2. **計画は構造化出力 1 回**（`LlmClient::generate_structured` で単一ツール `emit_plan` を強制）。
   中身は `[{ path, action: create | edit, instruction }]`。**計画はエンジンが検める**:
   パスの形（`editor::validate_rel_path`）/ カテゴリ（scenarios・characters・memoria・package.yaml・
   campaign.yaml）/ `create` は不在のファイルだけ・`edit` は在るファイルだけ / 新規名の規則
   （`create_file` と同じ規則・予約 id `player`/`party`/`*`）/ 件数上限（既定 12）。却下は理由を積んで
   **再計画 1 回**（#42: 何をすれば通るかを語る）。
3. **計画は作者に見せてから走らせる**（未決 1 → 確定）。各行の指示を書き換え・外せる。動かす前に
   費用の見当（ファイル数）がつき、方向違いを 1 往復で直せる。
4. **順序は機械が決める** — `package.yaml` → `characters/*` → `memoria/*` → `scenarios/*` →
   `campaign.yaml`（参照する側を後に）。モデルに順を任せない。
5. **各ファイルは既存の 1 ファイルループ（`run_edit_loop`）で書く**。道具も 5 本のまま
   （`read` / `grep` / `sd` / `diff` / `spec`）。**ファイル全体を書く道具は作らない** —
   新規ファイルは `editor::create_file` と同じ**雛形**を初期本文にして、モデルは `sd` で足していく。
   `sd` の差分上限（12,000 字）がそのまま「ブロックごとに足す」を強いる（置換のたびに診断が返る輪も
   そのまま効く）。
6. **ステージング = 一時フォルダの写し**。開始時にパッケージの YAML（package.yaml・campaign.yaml・
   scenarios/・characters/・memoria/）を一時フォルダへ写し、各ファイルのループは**そのフォルダを
   編集ルートにして**回す。1 ファイル終わるたびに作業本文をそこへ書く。これで足りないもの 1〜3 が
   **既存コードを変えずに**解ける — `read`/`grep` は前のファイルの結果を読み、`build_vocabulary`
   は前のファイルで宣言した id を拾い、`inspect_package` はファイル間の参照を検める。
   **新しい検査規則はゼロ**（spec 28・29 と同じ収縮）。アセット名（images/audios）だけは写さず
   元のフォルダから取る（写すと重いうえ、AI 編集はメディアを扱わない）。
7. **ファイルごとに文脈を新しく組む**。system は spec 29 と同じ構成（種別ごとの断片・既知キー表・
   id 表）に、**計画全体の一覧とこのファイルの役割**を 1 節足すだけ。前のファイルの会話は積まない
   （積むと「一気に」へ戻り、入力も膨らむ）。前のファイルの結果はステージングの本文と id 表で届く。
8. **全部書き終えたら層 2 の検査**（`inspect_package(ステージング)`）。**エラーか警告**を持つ
   計画内のファイルに修復ループを 1 回ずつ（死んだ参照は `Scenario::lints` = 警告側に出るので、
   エラーだけだとファイルをまたぐ整合の本命を取りこぼす）（`editor_lint::attribute_file` で帰属・帰属できないエラーは結果に添えるだけ）。
   それでも残れば**残ったまま**結果に載せる（spec 29 決定 9 と同じ — 捨てるより作者が直せる状態に置く）。
9. **結果は変更セット**（未決 2 → 確定）。ファイルごとに `新規` / `変更` / 差分 / 残った診断。
   **ディスクに書くのは作者**（「すべて適用」と「選んで適用」）。書き込みは既存の経路
   （`save_with_fork` / 作成）で、書庫版ならフォーク確認は 1 回。
10. **衝突の検出** — 開始時に各ファイルのディスク本文の hash を控え、適用時に変わっていたら
    そのファイルは書かずに「実行中に変更されたので適用していません」と出す（黙って上書きしない）。
    実行中は編集モード全体を読み取り専用にする（spec 29 の「同時に書く者を一人に」の拡張）。
11. **始める前に未保存を片付ける** — 開いているファイルに未保存の変更があれば、既存の未保存確認
    （保存 / 破棄 / キャンセル）を通す。spec 29 は未保存込みの本文を渡したが、複数ファイルでは
    「適用でその未保存分もディスクへ書かれる」が分かりにくいので、先に確定させる。
12. **停止性** — ファイル数の上限（既定 12）/ ファイルごとの周回上限（既存の 20 — 最後の 1 周はまとめ — + 上限の外の修復 1）/
    キャンセル（ファイル境界と周回境界で効く）。**止めても書き終えたファイルは変更セットに残る**
    （2026-09-10 の「中断すると全部無駄になる」懸念と同じ線）。
13. **削除・改名・メディアは引き続き作らない**（未決 4 → 確定）。計画に `delete` / `rename` は無い。
14. **モデルは `EDITOR_LLM_*` > GM の設定**（spec 29 決定 10）。利用量は spec 30 の `editor` 役に載る。

## 費用の見当（spec 29 Phase E の実測から）

1 ファイルの編集は 4〜10 周・入力 1.8 万〜28 万トークン（うち 5〜9 割がキャッシュ読み）だった。
6 ファイルなら単純計算で**入力 11 万〜170 万トークン**で、新規ファイルは雛形から足していくので
多い側に寄ると見る。計画の画面にはファイル数と、

## 何を作るか

### A. harness（純関数 + fake で固定）

- `edit_assist::Plan { files: Vec<PlanItem { path, action, instruction }> }` + `validate_plan(plan, existing_files) -> Result<Vec<PlanItem>, Vec<String>>`（決定 2 の検査と決定 4 の並べ替え）。
- 計画用の素材（`plan_messages(request, files, ids_table)`）: 大原則と構造の断片 + 各種別の 1 行要旨 + 今あるファイルの一覧と id 表 + 作者の依頼。
- `run_build(chat, plan, staging, cancel, progress) -> BuildOutcome`: ファイルごとに雛形の用意 →
  `run_edit_loop` → ステージングへ書く → 最後に `inspect_package` → 修復 1 周ずつ。
  `BuildOutcome { files: [{ path, action, before, after, diagnostics, summary, stopped }], package_diagnostics, usage }`。
- `ToolChat` / `ToolExecutor` の依存性逆転はそのまま（PoC は scripted fake）。

### B. CLI `play build <dir> "依頼…" [--plan-only] [--write]`

GUI より先に CLI で測る（spec 29 と同じ順）。既定はディスクに書かず、計画・各ファイルの差分・
診断・利用量を表示。`--plan-only` は計画だけ出して止まる。`--write` で変更セットを書く。

### C. app

command `build_plan(instruction)` / `build_run(plan)` / `build_apply(paths)` / `build_cancel` +
進行イベント `edit-build-progress`（ファイル名つきの 1 行）。ステージングは app_data 配下の一時
フォルダ（実行ごとに作り、適用か破棄で消す）。

### D. UI

AI 編集のパネルに**「このファイル」/「パッケージ全体」**の切り替え。パッケージ全体では:
依頼欄 → 「計画を立てる」→ 計画の一覧（行ごとに 新規/変更・パス・指示の編集・外す）→
「実行」→ ファイルごとの進行 → 変更セット（ファイルを選ぶと差分、`すべて適用` / `選んで適用` /
`破棄`）。適用後はファイル一覧・語彙・層 2 の検査を取り直す。

## 新しいパッケージを作る入口（未決 3 → 確定: ウィザードは変えない）

ウィザード（spec 28 追補）が作る骨格（package.yaml + `scenarios/main.yaml`）は既に読める形なので、
**骨格を作った直後に編集モードでこのパネルを開けば**「あらすじからパッケージを組む」が成立する。
推奨はこの形（ウィザードは変えない）。ウィザードに「AI に書かせる依頼」欄を足して作成直後に計画まで
進める形もありうる。

## PoC 方針

- 計画の検査: 形の悪いパス / 在るファイルへの create / 無いファイルへの edit / 予約 id / 件数超過を
  理由つきで拒否・並べ替えが依存の向きどおり。
- オーケストレーション（fake）: 前のファイルで宣言した場所 id が次のファイルの id 表に載る /
  新規ファイルが雛形から始まる / 他ファイルへの `sd` は従来どおり拒否 / キャンセルで書き終えた
  ファイルが残る / 層 2 のエラーで修復周が帰属先のファイルにだけ走る。
- 衝突: 実行中にディスクの本文が変わったファイルは適用されない。
- live は `--ignored` 1 本（骨格から短いパッケージを 1 つ組む）。

## Phase A で決めたこと（2026-11-23、実装で詰めた点）

- **層 2 で直させるのは「開始時に無かった指摘」だけ**。`Staging::prepare` で一時フォルダの層 2 を
  控え（baseline）、組み立て後の指摘から差し引く。作者が持ち込んだ指摘を AI に直させると、頼んで
  いないファイルや箇所に手が入る。件数だけ `preexisting_issues` で返す。
- **修復はエラーと警告の両方**（決定 8 を起草時の「エラー」から広げた）。死んだ参照は
  `Scenario::lints` = 警告側に出るので、エラーだけだとファイルをまたぐ整合の本命を取りこぼす。
- **読み込みエラーの帰属**。`inspect_package` の読み込みエラー（`HarnessError` の
  `{label} ({path}): {detail}`）は接頭辞を持たず、`attribute_file` は帰属できなかった — cast の
  定義不在や scenario の整合性エラーという、組み立てで最も起きやすい失敗が「パッケージ全体」に
  落ちて修復の行き先が無かった。括弧の中のパスの末尾で帰属させる（cast の定義不在は、パスが
  存在しない定義ファイルを指すので cast を宣言したシナリオへ）。エディタの層 2 一覧にも効く。
- **一時フォルダは LF**。道具の `(?m)^…$` は CRLF の `\r` の前で止まらないので、写すときに LF へ
  そろえ、適用で元のファイルの改行に戻す（新規は LF）。`play edit` と同じ扱い。
- **一時フォルダがパッケージと重なれば拒否**。`prepare` は既存の一時フォルダを消して作り直すので、
  呼び出し側が誤った場所を渡したときに消してはいけないものを消さない。
- **新規ファイルの LLM 失敗**。本文が変わらないまま呼び出しが失敗したら、置いた雛形を一時
  フォルダから消す（空の雛形を変更セットに出さない）。
- **衝突の比較は改行を LF にそろえて行う**（改行だけの違いは衝突にしない）。

**接地の限界**: 全部 fake のループで固めた。実モデルが計画をどれだけ一発で通すか、新規ファイルを
`sd` だけで何周で埋めるかは Phase B の実測が最初になる。
